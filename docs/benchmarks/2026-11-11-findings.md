# Latency findings, 2026-11-11

The numbers are in [2026-11-11.md](2026-11-11.md) (generated by `make bench`). This note explains
what they mean. Setup: this laptop's CPU (no GPU), 20 synthetic caller utterances per config
(10 English, 10 Urdu) played in real time through the real pipeline, free-tier cloud services.
Time zero is when the caller's audio really ended.

## Where a turn's time goes (Groq-answered turns, Piper voice)

| Stage | P50 | Note |
|---|---:|---|
| VAD notices the caller stopped | ~225 ms | Silero's `stop_secs` 0.2 plus a frame |
| Groq Whisper transcript | ~380 ms | runs only after VAD fires (segmented STT) |
| Smart Turn releases the turn | ~5 ms | not a bottleneck |
| LLM first text | ~700 ms (120b), ~1,060 ms (20b) | **~4,400 ms when Gemini answers** |
| TTS first audio after that text | ~290 ms | Piper, first chunk at a comma (`clause`) |
| **Caller stops -> agent audio** | **~1.8-2.0 s** | goal was < 1 s |

| Change (config) | Effect | Evidence |

## Barge-in

With the agent mid-sentence, Pipecat interrupted the reply about 370-390 ms after the caller
started talking (Silero needs `start_secs` 0.2 of speech plus confidence). The audio stopped
12-37 ms after that, with no audio played after the interruption. The context kept only the
sentences that were played in full. `test_barge_in.py` checks the same thing in CI without
models. Runs where the agent was silent at that moment (Kokoro pauses between slow sentences)
are flagged and not counted.

## Why we don't reach 1 s on the free tier

STT (~0.6 s from the end of speech, including VAD), LLM (~0.7 s) and the first TTS chunk
(~0.3 s) already add up to ~1.6 s on the best path. Getting under 1 s needs one of these:
- streaming STT with partial transcripts, so the LLM can start before the transcript is final;
- a faster first token: Groq's best free model is a reasoning model, and the paid tier lifts
  the daily cap that pushes turns onto Gemini;
- speech-to-speech (Gemini Live), which skips the hand-offs.

All three are options for later, recorded in DECISIONS (D23, D30, D31).

## What the run taught us about the free tier

Groq's free tier has a **200k tokens/day per model** cap besides 8k tokens/minute. The
benchmark used up gpt-oss-20b's day, and from the `prewarm` config on, Gemini answered almost
every turn. That's why those configs look slow; the stage table and the by-model table separate
the two effects. The fallback now shares rate-limit state across calls and models the bucket's
refill (D31).

## Azure voices (`azure` config, added after the owner set up an Azure key)

| | Piper (local) | Azure (UAE North) |
|---|---:|---:|
| TTS first audio after LLM text, P50 | ~290 ms | ~720 ms |
| First audio on Groq-answered turns, P50 | ~1.8-2.0 s | ~2.5 s |
| Barge-in: audio stops after the interruption | 22-40 ms, nothing leaked | 404 ms, 9 chunks leaked |
| Context keeps after barge-in | whole sentences | the words actually spoken (word timestamps) |

Azure sounds clearly more natural in both languages, but it adds a network round trip, and in
this run audio kept arriving after an interruption. That needs a fix before Azure becomes the
default. Samples: `data/samples/azure-*.wav` vs `piper-ur-*.wav` (git-ignored). The same run
showed English questions answered in Urdu by gpt-oss-20b and Gemini (`en07`-`en09`). That's a
reply-language bug independent of the voice, and it's next on the list.
